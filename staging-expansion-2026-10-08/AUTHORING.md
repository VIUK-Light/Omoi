# 4,710問への未承認案を作成する

記録日：2026-10-08（日本時間）。ユーザーは配分分析を受け「やろう」と指示した。**全3,768問の候補作成・レビュー・検証を進める。正本への反映は、具体的な最終案を示して確認後。**

## 作業範囲

最初に `AGENTS.md`、`OMOI_PHILOSOPHY.md`、`QUESTION_DATA_SCHEMA.md`、READMEを読む。`assignments.json`に各担当のカテゴリー別・Level別追加件数がある。自分の `shards/<担当名>/` だけを編集する。他担当・正本4ファイルは編集しない。

現行942問の原文と背景を確認し、`research/addition-analysis-2026-10-07/` の分野別分析・代表28案・独立レビューを利用する。担当に該当する代表案を必要に応じて含め、背景・感度・視点・警告まで整える。テーマの名前が新しいだけでは独立した問としない。

## 文面

- Omoiは普段聞かなかった相手の感覚・経験・価値観と理由を知る、重い話・深い問いの入口。ディベートの賛否だけへ寄せない。
- **全問を個別に書く。** 同じ文型へ人物・対象・数字を差し替え、語尾を変えて数を満たす生成は禁止。複数のLevelで主題が関連しても、聞ける感覚や判断対象が別になる理由を残す。
- L1は短く身近な入口。L2は具体的な日常・集団・境界。L3は社会・制度・役割の判断。L4は本人の利害・倫理・意味・葛藤を自分に置ける問い。仮の場面で答えられ、体験の告白を求めない。
- 主語、判断対象、比較条件を明示する。片方を明白に悪い人物にせず、唯一の模範回答へ誘導しない。「あなたなら？」だけ足してL4にしない。
- L3/4には**個別の**背景を付ける。何が架空条件で、どの価値・立場・不確実な点が関わるかを短く説明する。問いの言い換えだけ、共通定型の「正解はありません」だけにしない。新しい法律・医療・統計の事実を根拠なく断言しない。
- 資料は前回確認済み資料を利用し、特定の事実主張をする時はその資料の対象・時点・確認範囲を保つ。追加検索は可能。資料が不要な架空の葛藤は架空と明示し、適当なURLを飾りとして添えない。出典がない背景は検証で警告になり、確認一覧に残す。
- `topic` は細かな会話軸。カードIDごとに別topicにするのではなく、意味のある小分類を使う。1つのtopicのカードを単純な人物×物の組合せで量産しない。
- `sensitivity` は配慮の必要度1〜4。`perspective` はL3/4のみ affected / actor / decision_maker / observer。役割で決め、割合のために書き換えない。L4の追加全体は affected 約38%、actor 約31%、decision_maker 約26%、observer 約4%を目安に、主要3視点の各20%以上を保てる役割の幅をつくる。
- 内容に応じた `content_warning` を付ける。許可値はスキーマの10種類のみ。センシティブな場面を数合わせで追加しない。

## 納品

`shards/<担当名>/additions.json` を作る。JSONの最上位は配列。各要素：

```json
{
  "card": {
    "id": "exp26-担当名-0001",
    "level": 4,
    "sensitivity": 3,
    "category": "正式カテゴリーID",
    "topic": "意味のある小分類",
    "question": "個別に作成した問い",
    "perspective": "affected",
    "detail": {"text": "この問い固有の背景"},
    "content_warning": ["必要な許可タグ"]
  },
  "reason": "既存との差、追加で相手の何を知れるか。問固有の理由。",
  "editorial": {
    "author_group": "担当名",
    "fact_status": "hypothetical または sourced",
    "related_existing_ids": ["実在する近い既存ID（分かる時）"],
    "representative_analysis_id": "対応する28案のID（該当する時のみ）"
  }
}
```

L1/2にはperspective・detailを無理に付けない。空のcontent_warning等は省略してよい。`detail.sources`を使う場合は `{ "title": "資料名", "url": "https://..." }` の配列。

`hypothetical`でも、架空の葛藤を考えるための参考資料を添えられます。その場合は`source_review_scope`に資料が支える範囲を記し、架空の条件が実際に起きた証拠として扱わないでください。`sourced`を使う背景には出典が必要です。出典の有無だけで、場面が架空か実在か、すべての記述が検証済みかを判定しません。

構造の組立て・通番・書出しのループは使ってよい。質問・背景・理由を少数のテンプレートから組合せ生成してはいけない。長い作業は分割ファイルで保存し、途中の件数を主担当へ報告する。必要ならヘルパー `authoring.py` を利用できるが、文面は個別に作る。

`AUTHOR_REVIEW.md` に件数、使った小分類、既存との比較範囲、資料確認範囲、自己レビューで直した点、残る懸念を記録する。全件を書いてから自分の文面を読み直し、担当カテゴリー別・Level別件数を一致させる。構造合格だけで意味や事実のレビュー完了としない。
